# research-agent 下一版产出质量改进计划

2026-11-27 · 建议版本 v2.3 · 待实施与验收

## 发布目标

同事给出一个实际研究问题后，能在约定的篇幅内读懂结论、比较方案、判断适用条件，并能回到原文复核关键判断。研究深度由证据覆盖、交叉验证及反证决定；交付篇幅由受众和用途决定。

本地已有需求澄清、论证大纲、研究卡、声明账本、质量评分卡、截图局部展示和总编辑流程。已有一份厂商比较样章。下一版在这些入口上改进，并验证整份报告。起点为 126 项测试中 125 项通过，剩余一项为 Chromium 启动退出导致的结构图 PNG 导出失败。

## 实施次序

| 阶段 | 主要改动 | 可检查的产物 |
| --- | --- | --- |
| 1. 固定基线 | 保存当前代码版本和本地差异、旧报告、原始来源集、资料截止日、模型配置与预算。为每个题目预先写下读者必须能回答的问题。 | 基线清单、旧稿、评审题与逐项评分标准 |
| 2. 分开设定研究深度和交付篇幅 | 启动时记录受众、用途、必答问题、交付形态和显式篇幅要求。取消大纲与研究卡默认逐章字数，同步更新各入口、README、总编辑和质检。一般性总字数越界给提示；显式硬约束按约定单位及统计范围检查。 | “深度研究＋简短决策报告”能通过；空稿、占位稿、缺证据的核心结论仍会被拦截 |
| 3. 在写作前完成归纳 | 研究员先为核心问题整理跨来源发现、原文位置、证据分歧和成立条件，再写章节。选型题按共同维度比较；机制题解释组件、交互与执行位置；趋势题先核对统计口径。复用现有问题、声明及证据 ID。 | 每项核心判断能定位到证据；只有厂商自述时如实标注；来源不足时，正文给出有限结论和具体缺口 |
| 4. 把样章方法推广到整份报告 | 在冻结声明账本前，调度方汇总跨章共识、矛盾和决策影响，需新增判断时退回研究员核证。总编辑据此写执行摘要、删掉跨章重复，保留反例。根据读者问题选比较表、机制图或趋势图；正文展示需辨认的原文局部，保留完整证据入口。 | 摘要能回答全篇问题；每项发现能跳到章节和来源；图题说明发现，图注给出口径，章节解释图中值得关注的差异 |
| 5. 完成整篇验收与导出 | 在相同输入下生成新旧版本，开展匿名对读。修复或定位 PNG 导出问题，在支持的干净环境用真实浏览器生成图片并检查中英文标签、裁切和链接。 | 两份完整新版报告、逐题对照记录、Markdown 与 HTML、PNG、测试及未通过项 |
| 6. 让同事可安装、可复现 | 共用同一份工作流和依赖检查。先完成 Claude Code、Codex 的干净环境安装，回归 Hermes；再按多宿主备忘完成 WorkBuddy 和 DSH 的入口与实测。 | 各宿主分别记录版本、安装方式、能力或替代执行方式、同题产物和阻塞；发布页按实际验证范围标注支持状态 |

### 防止篇幅调整造成质量倒退

用短而完整、表格承载主要论证、仅有标题、只有表格但缺少解释、核心问题漏答、用户显式限定篇幅等样例做回归。自动检查文件、引用和元数据的完整性；评审人核对证据是否支撑原句、分析图是否准确表达关系。沿用历史数据兼容策略，新增元数据不强制旧课题迁移。

## 如何判定有明显改善

首轮选两类完整报告。用《国内外网安厂商 AI 安全产品竞争格局》检验比较与归纳，用《MCP Gateway》检验架构解释与适用边界。《AI 攻击动态防护》第三章继续作为长截图和五家厂商对比的专项回归。随后选一道未用来调整模板的新题，跑一次从澄清、检索到交付的完整流程，检验能否迁移。

同题对照分两步。第一步冻结输入材料，比较写作、归纳与绘图的变化。第二步在新题上开放真实检索，考察证据获取、反证和资料缺口。保存题目、预算、耗时与实际产物，避免把新增来源或更大的预算算成写作改进。

| 维度 | 怎么检验 | 建议的首轮验收条件 |
| --- | --- | --- |
| 回答问题 | 按预先登记的必答题逐项核查 | 每题有直接回答，或明确现有证据为何不足 |
| 判断可靠 | 核查执行摘要中的全部核心判断，追到原文位置，并检查支持与反方材料 | 核心判断全部可追溯；出现无支撑的确定性结论、口径误用或遗漏关键反证，退回对应章节 |
| 读者能否用起来 | 两位目标读者匿名、交叉顺序阅读新旧稿，分别回答五道相同问题。答案按事先定义的要点计分，同时记录耗时 | 建议两份新版的答题正确率均不下降，且每份报告平均多答对至少一题，或在正确率不降时平均用时减少至少 20%；记录分歧和实数 |
| 图表与截图 | 给读者看关键图表，请其说明能支持的判断与边界；逐一打开证据局部和原图链接 | 关键图表可正确解读；来源、单位及必要条件可见；正文长截图不会阻断连续阅读 |
| 工具链与安装 | 运行自动回归、真实 PNG 导出和宿主干净环境冒烟测试 | Markdown、HTML、PNG 和证据链接均可打开；每个宣称完整支持的宿主均实际跑通同一任务 |

上述数量和百分比是建议的版本验收目标。小样本结果逐份披露，保留读者的具体误读和修订记录。若首轮没有独立读者，可先产出机器回归与内部评阅结果，并将读者验收标为待完成。

## 发布顺序

第一轮先交“固定题目和来源 → 篇幅规则调整 → 一份完整新稿和旧稿对照”。确认归纳与可读性改善，再扩展到第二类报告、新题和宿主验证。Claude Code、Codex 优先交付可试用版本；Hermes、WorkBuddy、DSH 的完整支持逐项以实测为准。DSH 暂按 DeepSeek Harness 规划，实施前核实具体产品。五宿主总体目标保留至各自端到端验证完成。

## 第一版测试与预算决策

第一轮以冻结来源的八章决策简报验证共享流程。留存历史 A 稿和材料哈希，B 试制稿执行需求约定、逐章比较、跨章综合、编辑、导出和严格质检。历史运行没有同口径的模型及 token 记录，因此这轮只能比较交付形态，正式 A/B 需在同一宿主重跑。C 使用同一模型及截止日，预算上限取 B 的 1.3 倍，增量优先用于影响结论的证据缺口、综合与图表复核。对比中分别记录实际支出、有效新增证据、读者正确率和耗时，再决定默认配置。

进入下一轮的顺序为厂商比较简报对读、MCP Gateway 整篇与新题检验、五宿主干净环境交付。通用入口和依赖随测试包共享，正式版的宿主支持声明按真实运行结果更新。
